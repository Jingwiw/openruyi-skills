# 改动边界与提交分组

从当前 diff 和用户期望的审阅方式出发。每组说明一个能被审阅和撤销的意图，而不是按文件、行数或工具运行次数拆分。

- 升级及让该版本正确构建、安装所必需的兼容修改通常应一起考虑；独立能力修复可以另组。格式整理是否单独成组，看它是否掩盖语义修改和仓库历史。
- 不固定提交数量。用户要求保留系列时不擅自 squash；如果边界明显需要调整，先给出新的分组依据。
- 后组依赖前组时标明依赖。每个中间提交能否构建、是否有意只形成最终可验收状态，应如实说明。
- 为纠正已发布主题分支里的错误，可以按授权修订原提交，不额外制造过程性修复提交；远端重写方式属于 Git 操作能力。
- 过程日志、下载缓存、凭据不属于产品 diff；测试和工具若是可维护交付物则不应仅因“不是源码”排除。

输出每组目的、包含路径/片段、依赖和相应验证；不以“整理提交”隐含推送或改写 main 的权限。
